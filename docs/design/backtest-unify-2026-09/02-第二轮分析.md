## 议题五：全局预览抽共用组件（各页面 URL 与效果保持不变）

### 目标澄清

不采用第一轮"方向 A"（下线两个页面跳转统一入口），改为：**一份组件代码，单产品页与多产品页各自加载，URL 不变、视觉与交互效果不变**。收益是后续只改一处。

### 现状事实（为什么现在是三份代码）

| 维度 | 单品预览页 | 多品预览页 | 结论 |
|---|---|---|---|
| HTML 骨架 | `templates/backtest_training/global_preview.html`(110 行) | `templates/backtest_multi_product/global_preview.html`(269 行) | 外壳（summary-panel/summary-card/#groupSelect/#previewContainer）同构；多品多 `#ratioPanel` + `#exportWordModal`；同一职能 id 不同名（导出按钮 `exportGlobalPreviewBtn` vs `exportBtn`，汇总卡 `summaryTotal` vs `summaryProducts`） |
| JS | `backtest_training_global_preview.js`(211 行)，DOMContentLoaded 内绑定 | `backtest_multi_product_global_preview.js`(728 行)，顶层直接绑定并立即加载 | 渲染核心（renderSummary/renderGroupOptions/renderActiveGroup）同职能不同实现；多品多比例编辑状态机（dirty/signature，:65-169）与 Word 弹窗组（:514-655） |
| payload | `{task, summary, groups[]}`，row 取 `values[column_key]`，列描述在 `groups[].columns[]` | `{task, summary, products, groups[]}`，row 取 `product_values[index]` + `weighted_*`，无 `columns[]` | **不同构**。同构字段仅 `group_key/group_label/failed_results` 与 row 的 `category/metric`（`backtest_report_query_service.py:841-978` vs `backtest_multi_product_preview.py:40-216`） |
| CSS | `backtest_training_global_preview.css`(146 行) | `backtest_multi_product_global_preview.css`(280 行) | 前 59 行几乎逐行相同；同名类值冲突（`.preview-table` min-width 960 vs 1100） |

组件化先例：`static/js/common/business/*.js` 全部是 IIFE 挂 `window.Biz` 命名空间（如 `Biz.returnSeriesExport.exportAndDownload({...})`，支持"值或函数"的 resolveOption）；`navbar.js` 是自渲染挂载点模式。**尚无 `create(container, options)` 工厂组件先例**，本次将是第一个。

### 实现方案（推荐）

**一个组件文件 + 一份组件 CSS，页面缩成挂载点 + 初始化调用。**

1. 新文件 `static/js/common/components/global-preview.js`，暴露工厂：

```js
Biz.globalPreview = { create: function(rootEl, options) { ... } };
```

   options 契约（建议）：
   - `mode: 'single' | 'multi'`——选择渲染策略与 payload 适配器；
   - `taskId`、`backHref`（返回详情链接，含分页参数透传）；
   - `api`：`load()`、多品的 `calculateRatios/updateRatios`（按 mode 注入）；
   - `features`：`{ ratioEditing, wordExport, returnSeries, xlsxExport }` 开关；
   - `exportNames`：下载文件名规则（两页现名不同）。

2. **统一渲染模型**（关键设计）：组件核心只认一套中间模型——`{summaryItems[], groups[{key,label,meta[],columns[],rows[{category,metric,cells[]}]}]}`。两个 mode 各写一个 payload→渲染模型适配器（单品读 `values[column_key]`，多品读 `product_values[index]`/`weighted_*` 并按 `ratio>0` 过滤列）。**核心渲染零分支，差异全部隔离在适配器**，这是"效果与当前一致"的保障。

3. DOM 策略二选一：
   - **B（推荐）页面 HTML 缩成挂载点**：`<div data-global-preview-root data-mode="multi"></div>`，组件全量渲染（navbar.js 模式的扩展）。id 冲突问题自然消失（组件内部用 root 内查询或生成的局部 id），一份模板保证两页视觉同构。
   - A（保守）保留两页现有 HTML，组件通过 `options.ids` 映射接管数据与事件——改造小，但 id 双轨长期存在，后续仍是两套骨架。
   - 多品的 `#exportWordModal` 弹窗作为组件内置 feature（mode=multi 才注册），HTML 一并进组件渲染。

4. CSS：新建 `static/css/components/global-preview.css` 收编两页公共段（现 1-59 行重复部分），页面差异用 `.gp-multi` 等 mode class 作用域化，解决同名类值冲突；两页各自的 page css 删除或只留壳层差异。

5. **必须原样保留的对外行为**（回归清单）：
   - `?ratios=` URL 入参解析与 `history.replaceState` 清参（`backtest_multi_product_global_preview.js:326-369`）——`weight_combination_tabulator.js:643` 以新标签带 `?ratios=` 打开多品预览页，是外部依赖；
   - 返回详情链接的分页参数透传（`buildDetailHref`，单品 :32-43）；
   - `return-series-export.js` 的引入顺序（utils.js 之后、页面 JS 之前）；
   - 多品"未保存比例预览"时 XLSX 导出拼 `?ratios=` 的行为（:414-426）。

6. 页面剩余物：两个页面 JS 各缩成 ~30 行初始化调用；模板缩成壳。预览中心页（`global_preview_index.js`）的 DOM 差异更大（查询表单、按股票/年份分组），本轮不动，后续可选复用组件的表格渲染部分。

### 风险

- 无构建系统下加载顺序与全局命名纪律（组件不得与页面 JS 重名）；
- 多品比例编辑的 dirty/signature 状态机逻辑较细，迁移时保持原实现原样搬，不重写；
- CSS 合并后两页像素级回归要靠 mode 作用域做对，建议以截图对照验收；
- payload 适配器要覆盖多品 `ratio=0` 过滤列与下标对齐的隐式约定（products[] 顺序即列顺序）。

### 工作量

中等：组件文件（渲染核心 + 两个适配器 + 多品 feature）约 600~700 行（两页现有 JS 去重后的合理体量），两页接线 + CSS 合并 + 回归。预览中心复用另计。

## 议题六：preview 接口 + 数据直驱 Word 导出 + v3 页面

### 结论

可行，且建议把"数据直驱导出"做成**纯渲染器**：`preview` 端点一次性完成全部业务计算与报告组装；`from-data` 端点只做 matplotlib 画图 + docx 组装，不再触碰指标引擎与任务重建。v3 页面 = bundle 的渲染壳 + 导出按钮。

### 现状事实

- Word 生成的计算集中在 `generate_word` 前半段：`_build_benchmark_runs`（每基准跑一次 V1 引擎）→ `_build_report_data`（组装 blocks JSON）→ `_build_chart_data`（图表序列 dict）→ 相关系数矩阵；后半段（`generate_report_charts` 画 PNG、`generate_word_document` 组 docx）是纯渲染（`strategy_backtest_report_service.py:64-107`）。
- docx 组装器 `word_export_template.generate_word_document` 只消费通用 blocks（heading/metadata/table/paragraph/bullet_list/image，`word_export_template.py:181-245`），与数据来源无关——**"传数据直接出 Word"没有结构障碍**。
- RPT-M 请求现会被 `export_backtest_word` 按任务重建 payload（`export_service.py:316-327`）；from-data 路径天然绕过该重建（bundle 自包含）。

### 数据契约（bundle）两个方案

| 方案 | preview 返回 | from-data 做什么 | 评价 |
|---|---|---|---|
| A 传原料 | runs 的 metrics + 各日收益序列 | 重跑 `_build_report_data`/`_build_chart_data` 再渲染 | 计算逻辑两端各留一份调用，块组装仍绑在后端服务 |
| **B 传成品（推荐）** | `{metadata, blocks[], chart_data, correlation, conclusion[], dates, benchmark_labels}` | 只画 PNG（chart_data→图表、correlation→热力图）+ blocks 组 docx | 计算 100% 收敛在 preview；from-data 与业务零耦合、最薄；blocks 可直接被 v3 页面渲染，**前端所见与 Word 同源同值** |

方案 B 的 bundle 校验：
- Pydantic 全层级 schema（blocks 的 type 白名单 + 各 block 字段模型、chart_data 序列形状模型）；
- 关键不变量校验：各序列长度 == len(dates)、benchmark 面板数一致、blocks 中表格列数与表头一致——保证渲染不炸；
- 明确边界：数值真实性不校验（内部工具 + `login_required` 可接受；伪造数据只会产出一份错误的文档，无落库、无注入面——python-docx 对文本自动转义）。

### 接口草案

```
POST /api/exports/backtest-reports/word/preview     ← 复用 StrategyBacktestReportSchema
  返回信封 data.bundle = {metadata, blocks, chart_data, correlation, conclusion, dates, benchmark_labels}

POST /api/exports/backtest-reports/word/from-data   ← 请求体即 bundle（BundleSchema 校验）
  返回 docx 文件流；缓存键 = bundle 规范化 JSON 哈希（可选，初版可先不缓存）
```

- preview 同挂 `_export_limit` 限流；不进现有 docx 磁盘缓存（键语义不同）。
- 现有"直跑"导出入口全部保留，两条路并存：直跑=可信计算；from-data=预览后导出（数据来源是 preview，正常流程下两者数值一致）。

### v3 页面

- 路由：`app/routes/pages/performance_analysis.py` 的 PAGES 表加 `("/v3", "performance_analysis/v3.html")` → `/performance_analysis/v3`，注册方式与现有页面一致（表驱动 `register_page_routes`）。
- **v3 本身零分析逻辑**：读取 URL 参数 → 调 preview → 渲染：
  - `blocks` 直渲染（metadata 表、表格、段落、结论；普通 script，参照 `Biz.result-table` 的表格渲染模式）；
  - `chart_data` 用 Chart.js 重画（净值/回撤/超额/月度超额分布等，与 Word 图一一对应）；
  - "导出 Word"按钮把页面持有的 bundle 原样 POST `from-data` 下载。
- URL 参数形态（决定 v3 的入口方式）：
  - 从 v2 进入：v2 分析完成后带原始请求参数跳转（或 sessionStorage 暂存请求体），v3 用它调 preview；
  - 从单品全局预览进入：带任务收益来源参数（RPT-S 形态）；
  - 从多品全局预览进入：带 `task_id + group_key + ratios + include_composite_benchmark`（RPT-M 形态）。
- 入口落位（按你的要求）：v2 页加"报告预览（v3）"按钮（**注意：v2.html 目前没有任何全局预览类入口**，唯一跳转是返回 `/performance_analysis/`，见 `v2.html:33`，所以是新增按钮不是改造）；单/多品全局预览页的工具栏各加"Word 预览"入口。

### 风险与工作量

- bundle schema 是主要工作量（blocks/表格/序列的全层级模型）；from-data 端点本身很薄（现成 `word_export_template` + `strategy_backtest_report_charts`）；
- v3 前端最大的活是 blocks 渲染器与 Chart.js 图组，样式可复用多品预览页 CSS；
- 与无风险利率改造天然联动：v2 弹窗的 rf 选择随请求进 preview，v3 所见即含 rf 的报告；
- 需要裁决：bundle 是否持久化（不落库则 v3 刷新必须能凭 URL 参数重算 preview，因此 URL 参数形态要一次定稳）。

## 议题七：config/result 统一格式 + 全层级 Pydantic 校验

### 现状痛点（全部有行号证据，此处浓缩）

**校验位置错位**：所有任务类型共用宽松的 `TaskCreateSchema`（`config: dict[str, Any]`，`app/schemas/task.py:39-43`），请求边界对 config 内层零校验；真正的校验/归一散落 20+ 个手写函数：`creation.py`（`_normalize_task_config_for_type`:159、C5/C7 kline_source:39、C7 random_price:75、C31 拆分 296-527 全手写）、`backtest_multi_product_service.normalize_multi_product_config`:169、`backtest_multi_product_service` 的 market/price/ratio 归一：57-96、`backtest_parameter_utils.normalize_backtest_training_config`:31、执行侧 `_c3_to_c5_get_config`:246 等；且 create/update/restart 三处重复走同一套（`creation.py:230/566-645/655-666`）。

**命名不统一（代表性证据）**：
- 表标识三形态：`sheets[]` vs `sheet{}` vs 顶层 `spreadsheet_id/sheet_name`（`base.py:1160-1224` 三者兼容）；
- 年份/区间四套：C3 `year_n("1y")`、C4/C5/C7 `date_range_mode`+`exclude_recent_years`（旧名 `exclude_years`，base.py:442-445）、training `full_years/recent_years`、multi `start_date/end_date`；
- 枚举不一致：price_mode 创建侧只许 kp/sp/vwap（creation.py:186-190），multi 侧额外许 ohlc_price（:61-65）；
- 双名/别名：`kline_data_source|data_source`、`stock_code|stock_no|code|symbol`、`stock_name|name_cn|product_name`、camelCase 的 `marketType/securityTypeName`（creation.py:106-137）；
- model_version 四种写法并存：枚举值大写 `google_sheet_C4`（models.py:270-277）、归一小写（task_types.py:8-24）、报告 `c7.0.3` 带点（backtest_report_metadata.py:8-21）、配置 `c7_0_3` 下划线（c7.py:147）。

**result 不统一（代表性证据）**：
- 旧包装结构 `{spreadsheet_id__title: {单元格键指标...}}`，每个消费端都要扫描 `payload.values()` 找核心 dict（`backtest_multi_product_service.py:241-269`、`backtest_api.py:234-246` 等，且带"迁移后可移除"的 TODO）；
- 键名别名表 `historical_metrics._LEGACY_KEYS`（sotino→sortino、excess_sharp→excess_sharpe 等 9 条，historical_metrics.py:13-23）；models.py:28-29 `start_sharpe_ratio`↔`sharpe_ratio` 回填；
- 同值异名：出库键 `maxdd/year_rate` vs 概念键 `max_drawdown/turnover_rate`（export_workbook_service.py:84-92 对照 `c_template_layout.py:63-73`）；契约键与存键错位（summary_contract vs result_mapper 三个例子）；
- 值格式：百分比字符串与小数两套并存、两套格式化器（`:.2%` vs `*100:.2f%`）、日期三种格式混用（见第一轮报告 3.5 节行号）；
- **result 无任何 Pydantic schema**；唯一统一对象是 dataclass `MetricsV1Result`（无校验）。

### 统一方案（分析）

**config 侧——"边界 discriminated union + 服务层单入口"：**

1. 每任务类型一个 config schema（嵌套模型到底：`SheetRefModel`、`ProductModel`、K 线参数模型……），`task_type` 作判别字段：`validate_config_for_type(task_type, config) -> 归一化后的 canonical dict`。
2. 现有 20+ normalize 函数**迁入**对应 schema 的 `field_validator/model_validator`（逻辑不改，只搬家），`validate_config_for_type` 成为唯一调用面，create/update/restart/execute 四点共用——消灭三处重复。
3. 旧名吸收用 Pydantic v2 `AliasChoices`（如 `kline_data_source|data_source`）：**读侧容忍、写侧归一**——校验通过后 dump 回 canonical 键名再落库，历史形状进来一次就被洗成统一形状，不是双轨。
4. **与"全库无兼容层"原则的关系**：历史 DB 行禁止迁移（AGENTS 红线），所以读侧别名表是永久性"单一规格"而非过渡兼容层；与 `historical_metrics._LEGACY_KEYS` 同一哲学。
5. 落地顺序必须按链路波及面倒排（config 形状牵动 8 条链路：创建/更新/重启/排队互斥/占用释放/执行合并/汇总重建/前端回填，证据行号见盘点报告第 6 节）：**P1 backtest_multi_product**（最年轻、normalize_multi_product_config 可直译成 schema）→ P2 backtest_training → P3 C5/C7（共享字段多，一起收）→ P4 C3/C4/C31（C31 拆分手写校验最多、收益最大但风险最高）。每期独立可回退（按 type 逐个切换，天然分批）。

**result 侧——"写侧收敛 + 读侧单表"：**

1. 目标契约已经存在：`metrics_payload {schema_version, metrics, canonical_metrics}` + 收益序列独立存 `TaskResultReturn`（`backtest_training_service.py:721-726` 注释即"统一存储契约"）。c3/c4/c5/c7 都已在写 metrics_payload，乱的只是**外层旧包装与旧单元格键**。
2. 定义 `ResultEnvelopeSchema`（Pydantic）覆盖 `{schema_version, metrics, canonical_metrics, flat_result?}`，写库前校验（先 warn 后 raise 两档切换）；`MetricsV1Result` 从 dataclass 升级或由 schema 包装。
3. 读侧别名统一收口：`_LEGACY_KEYS`、`start_sharpe_ratio` 回填、extractor `field_map` 已是事实上的读侧规格表——把它们与 `app/constants/` 的定位对齐（纯数据表），消费端只准经它取值，禁止再私接旧键。
4. 值格式规范一条：**存储一律小数 + ISO 日期**，百分比只是展示层格式（收敛为单一 `format_percent` util，消灭 `:.2%` 与 `*100:.2f%` 双实现）；model_version 裁决单一形态（建议：内部枚举小写下划线 `c7_0_3`，显示层唯一出口转 `C7.0.3`）。

### 风险与工作量

- 四项议题里最大的一项；config 侧每期都要过 8 条链路回归（重启、占用、互斥排队是高风险点——它们靠 `spreadsheet_id` 提取做互斥，schema 化时不能丢字段）；
- 前端回填依赖 `Task.to_dict` 原样返回 config（models.py:357），归一化会改变前端拿到的键名——**前端详情/重启回填要同期适配**（这正是 AGENTS"改字段要同步检查五处"的放大版）；
- 建议先出"字段规格表"（放 `app/constants/`，仿 c_template_layout.py 先例）再写 schema，避免 schema 直接编码散落事实。

## 议题八：多品修复 + 更高效的 Sheet 处理方式

### 先回答"修复"：最小风险修复集（沿用第一轮结论，含新证据）

1. **循环内连接复用**：`_init_google_sheet` 从"每步必调"（`backtest_multi_product_service.py:859`）改为"spreadsheet 变化才重建"；`GoogleSheet._connect_and_select_worksheet` 每次都 authorize+open_by_key（`google_sheet_client.py:54-68`），同表 N 产品省 N-1 次完整重连。
2. **K 线指纹跨产品跳写**：`sheet_kline_cache` 条目加指纹（源键+长度+首尾日期），同表换产品指纹一致则跳过滞空+重写（现 :868-872 强制 rewrite）；多品 K 线长度天然一致（共享起止日期），该优化命中率应接近 100%。
3. **按需清尾**：仅新 K 线比上次长才 clear 尾部，否则整段覆盖写（滞空上界现用历史最大长度 `column_A_length+2`，:867/:564）。

### 关键新事实：Sheet 本身就是计算引擎，Sheet IO 无法绕过

单组合完整流程（`backtest_training_service.py:518-748`）：

```
写参数（+K线，仅源变化时）→ update_jumped_cells（一次 HTTP，update_cells(Cell 列表)，client.py:288-329）
→ 轮询读 output_range（最多 60 次/约 20-30 秒，_poll_google_sheet_completion :731）
  —— 等的是 Sheet 内模型公式对输入变化的响应（对比 initial_results 快照判断"未完成"）
→ get_ranges 批量读结果区与收益列 → 本地 calculate_v1_metrics 算指标
```

C3/C5/C7 模型以表格公式形态存在于 Sheet 中，K 线写入是模型计算的输入，**不能不写**；优化空间只在"写多少次、等多久、读多宽"。

### 更高效的 Sheet 处理方式（按性价比排序）

| # | 方式 | 收益 | 风险/前提 |
|---|---|---|---|
| 1 | 指纹跳写 + 按需清尾（上述 2、3） | 每次产品切换省 1 次 clear + 20 秒盲等 + 全量重写 | 低；纯后端，指纹必须含首尾日期防脏输入列 |
| 2 | 循环内连接复用（上述 1） | 省 N-1 次 authorize + open_by_key 网络往返 | 低；注意连接对象生命周期与任务取消/看门狗对齐 |
| 3 | **块状写入**替代散点更新：K 线是"日期列+值列"矩形区，用 `worksheet.update(range, matrix)`（每列一次或两列一批）替代 `update_cells(1200+ 个散点 Cell)`——同等单次 HTTP 下请求体从 N 个离散条目变 1 个矩形块，载荷小、不受散点条目规模约束 | 写入耗时下降（大序列明显） | 中低；**须核对 value_input_option**：日期字符串被 Sheets 自动识别为日期/或模型列期待文本，现 `update_cells` 行为是基线，切换前要用真实模板验证一次 |
| 4 | 盲等 20 秒 → **写后回读校验循环**（回读刚写入的输入区比对一致即继续，小间隔+上限） | 常态下省大半 20 秒；比固定等待更可靠 | 中；"20 秒"在仓库文档中无官方解释（grep 无记载），属经验值——它可能在等模型对"清空"的响应，因此回读对象应是**写入的输入单元格**而非输出区；建议先在一个测试表上试点量化 |
| 5 | 轮询节奏自适应（前密后疏/指数退避） | 模型算得快时提前结束（现固定节奏 60 次） | 低；`_poll_google_sheet_completion` 是共享骨架，改节奏要全任务类型回归 |
| 6 | **每产品独立工作表（tab）**，K 线各写各的 tab，组合间只改参数单元格 | 从结构上消灭 clear/等待/重写冲突 | 高；Sheet 模板公式要改为引用各 tab（模板即业务模型，改模板牵动业务口径），且需 tab 生命周期管理——**单列为长期项，不与 1-4 同批** |

### 收益量化（3 产品共用同一 Sheet 的任务，估算）

- 现状：每次产品切换 = 重连 + clear + 20 秒盲等 + ~1200 行全量重写；整任务至少 2 次产品切换。
- 修复 1-4 后：0 次重连、0 次重写、0 次清空盲等（写后校验通常秒级通过）；每组合只剩 2 个参数单元格写入 + 结果轮询读取——Sheet IO 几乎降到底线（轮询读取由 Sheet 模型计算时间决定，无法再压）。

### 决策点

1. 修复 1-3 是否同批做（低风险三件套）？
2. 块状写入（#3）是否先做真实模板验证（value_input_option 与日期格式）？
3. 盲等改回读校验（#4）是否允许先试点（单任务灰度观察日志）？
4. 每产品独立 tab（#6）是否立项（涉及 Sheet 模板改造，需要模板侧配合）？
