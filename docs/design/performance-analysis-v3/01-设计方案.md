> 2026-09-30。V3 页面（`templates/performance_analysis/v3.html`）当前是 V2 的直接复制

## 0. 已确认决策与新增问题结论

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 涨跌色约定 | **红涨绿跌**（国内习惯）。所有正负着色（KPI、表格、热力图、瀑布/柱状）统一执行 |
| 2 | 净值/累计收益序列数据源 | **后端导出**：analyze 响应增加 `series` 载荷（详见 §2.3），前端不复算复利净值 |
| 3 | v3 前端文件 | **新开** `performance_analysis_v3.js` / `performance_analysis_v3.css`，v2 页保持稳定零影响 |

新增四问的结论（详细论证见对应章节）：

1. **无法绘图的数据 → 表格化**：可以，且不自创分组——直接对齐 RPT-S Word 报告的**八章表格体系**（§6）。
2. **V2 原有 12 个明细 tab 评审**：全部保留但重组——3 个比率 tab 合并、关键标量中文化改造、Sheet 结果条件显示（§6.2）。
3. **Sheet 结果 / 任务跳转数据展示**：`sheet_result` 有则显示；C 系列/回测跳转经 `?task_id=` / `?result_id=` 直达（§7）。
4. **统一中英文映射**：需要。新建 `static/js/common/metric-names.js` 前端唯一词表，V3 全部消费（§8）。

## 1. 背景与目标

### 1.1 现状事实

- `POST /api/performance-analysis/analyze` 是唯一分析入口（2026-09-30 合并 analyze/analyze-sheet/result 三来源），
  响应 `{ok, message, data:{results, metrics}}`。**`data.results` 即全量指标字典（150+ 键），`data.metrics` 恒为 `{}`**
  （`text_analysis.analyze` 只放 `results`，`metrics` 键被注释）。
- metrics 产出已大幅扩展（`metrics.py::_calculate_metrics_v1`），V2 前端只渲染了约 30 个键。
  未可视化的新增指标：累计收益/超额净值、滚动收益 3/6/12 月（均值+胜率）、月度/日度/超额收益分布（7 桶+占比）、
  偏度/峰度、连涨连跌月数、创新高统计（次数/频率/平均间隔）、极端行情（下跌/上涨阶段月数/均值/胜率/跑赢次数）、
  日度盈亏比、极端单日统计、期初期末净值、单日大跌次数/频率等。
- V2 前端 11 张图几乎全是"指数 vs 模型"年度分组柱/线；信息层级"表格优先、图表垫底"（卡片标题即"V2 图表（底部）"）。
- **核心数据缺口**：analyze 响应没有净值序列。后端 `facade.calculate_v1_metrics`
  （`facade.py:105`）已 `return_dataframes=True` 产出 `index_df/start_df/excess_df`（含 `net_value` 列），
  但 `text_analysis.analyze` 只取 `.metrics`，三个 DataFrame 被丢弃。
- `sheet_result` 只在 Google Sheet 来源（`sheet_reader.analyze_v1`）返回，内容是 C 模板 Sheet 自带的结果区键值对：
  C3 取第 15~23 行 `Parameter_H/Value_I`；C7/C5/C4 取 `result_key_C/result_values_D` 列；C7.0.3 取 `C2:D20`。
- V2 `fillScalarsTable` 里已有一份 14 条的硬编码映射 `scalarNameMap`（英文键→中文名），是统一词表的种子。

### 1.2 目标

1. 更丰富的图表化：补齐量化报告的"第一图"（净值曲线、水下回撤、月度热力图），把新增指标全部图形化。
2. 排版重构：从"表格优先"改为"图表优先 + 明细折叠"，分区仪表盘 + sticky 锚点导航。
3. 多数据对比接入口：前端 Dataset Registry 分层，未来任意新数据源注册即可对比，不改图表层。

## 2. 数据契约与后端改动

### 2.1 analyze 响应（现状，V3 继续消费）

```
POST /api/performance-analysis/analyze
载荷（三选一）：{ result_id } | { spreadsheet_id, google_sheet_name } | { data }
公共：runtime_params { market_downturn_threshold, market_upturn_threshold,
                       daily_extreme_threshold, daily_drawdown_threshold, risk_free_rate }
响应 data.results = 全量指标字典；data.metrics = {}（恒空，V3 不消费）
```

### 2.2 指标产出分组（按 Word 报告八章对齐）

| 附 | 口径回显 | `market_downturn_threshold`、`market_upturn_threshold`、`daily_extreme_threshold`、`daily_drawdown_threshold`（V3 渲染成"本次口径"chips） |
| 附 | Sheet 结果 | `sheet_result`（仅 Sheet 来源） |

### 2.3 后端唯一改动：导出净值序列（已确认走后端）

**原则**：不新增端点，单一执行路径加一个可选载荷，缺省行为不变（V2 零影响）。

```
POST /api/performance-analysis/analyze
载荷新增可选：include_series: true
响应 data 新增：series: {
    "dates":      ["2024-01-02", ...],   // index_df['date'] ISO 序列
    "index_nav":  [1.0, 1.0032, ...],    // index_df['net_value']
    "start_nav":  [1.0, 0.9975, ...],    // start_df['net_value']
    "excess_nav": [1.0, 1.0057, ...]     // excess_df['net_value']
}
```

- 实现：`text_analysis.analyze` 现在只取 `calculate_v1_metrics(...).metrics`，改为先持有
  `MetricsV1Result`（`facade.py` 已带 `index_df/start_df/excess_df`），按 `include_series` 拼装 `series`；
  `sheet_reader.analyze_v1` 同步。`include_series` 经 `service.analyze(payload)` 透传
  （`_analyze_text` / `_analyze_sheet` / `_analyze_result` 三个分支都要透传）。
- 请求 Schema（`app/schemas/performance_analysis.py` RootModel 自由字典）无需修改；来源分流留在 service。
- **仅 dual 模式导出**：`analysis_mode=single`（单列收益，无基准）走旧 `_calculate_metrics` 管线，无序列可导，
  `series` 置 null，前端降级隐藏曲线区（§4.4）。
- 体积：日线约 250 点/年，5 年约 1250 点，全量 JSON 数十 KB，可接受；>5000 点等距抽样到 ≤2000 点登记为可选优化，一期不做。
- `canonical_metrics`（facade 已算好的基准/策略/超额分组）是否随响应透出：**可选后续项**。
  一期 V3 KPI 直接从 `results` 取键 + 词表取名即可，不强制。

### 2.4 任务跳转入口的数据可行性

- 结果列表：`GET /api/tasks/<task_id>/results?fields=id,task_id,parameters,return_series_id,success,return_date_range`
  （fields 白名单投影已上线，见《2026-09-30-全局预览Word导出》文档），V3 结果下拉直接复用。
- 单结果详情：`GET /api/results/<id>`（V2 结果分析直输 ID 路径已在用）。
- C 系列详情页已有"全局预览"直达先例（`?task_id=` 自动查询）；backtest_training / multi_product 任务同契约。

## 3. 视觉与颜色约定（已确认红涨绿跌）

| 语义 | 颜色 | 用途 |
|---|---|---|
| 系列-基准（指数） | 蓝 `#0d6efd` | 净值线、年度柱、表格"指数"列 |
| 系列-策略 | 绿 `#198754`（Bootstrap success，页面主对比色） | 同上"策略"列 |
| 系列-超额 | 橙 `#fd7e14` | 超额线、超额柱 |
| **涨=红** | `#dc3545`（danger） | 正收益数字、热力图正值格、上涨阶段 |
| **跌=绿** | `#20c997` 或 `#198754` 的浅阶 | 负收益数字、热力图负值格 |

- **系列色与涨跌色严格分离**：系列色只标识"是谁"，涨跌色只标识"方向"。热力图/水下图/正负柱才用涨跌色。
- 页面顶部图例区固定放一句约定说明（"红=正/涨，绿=负/跌"），避免歧义。
- 数字规范：统一 `fmt` 帮助函数——百分比固定 2 位小数、比率 2 位、净值 4 位；千分位；正负着色；
  表格数字右对齐等宽字体；每行最优值（策略占优格）描边高亮。

## 4. 信息架构：分区仪表盘

```
① 顶部：标题 + 口径 chips（四个阈值 + 无风险利率，取自响应回显键）+ 来源信息卡（任务/股票/年份/参数/K线范围）
② 核心 KPI 三列卡：基准 | 策略 | 超额（对应 canonical 语义）
   累计收益、年化收益、最大回撤、夏普、索提诺、卡玛 + 超额区（累计超额、月超额胜率、跑赢年份）
③ 净值与回撤区：净值曲线（基准/策略/超额，可切换对数轴）+ 水下回撤面积图（同一时间轴联动）
④ 年度绩效区：年收益分组柱、年回撤、年超额柱、风险调整比率（卡玛/索提诺/夏普年度对比）
⑤ 月度透视区：月度收益热力图（年×月）、月超额收益柱（正红负绿）、滚动收益 3/6/12（均值柱+胜率线）
⑥ 收益分布区：月度/日度/超额三张直方图 + 偏度峰度标注 + 月度散点图（指数x-策略y + 45°线）
⑦ 风险与极端行情区：下跌/上涨阶段对比、极端单日、修复天数、连涨连跌、创新高统计卡
⑧ 数据明细（折叠）：按 Word 报告八章组织的表格区（§6）+ Sheet 结果（条件显示）+ 全量 JSON（兜底）
```

- 左侧 sticky 锚点导航（②~⑧），滚动高亮当前分区。
- KPI 卡结构：标签（中文，词表）+ 大数字 + 基准/策略/超额三列，策略列带相对基准的 delta 徽章（红涨绿跌）。
- 图表卡统一高度（320px 网格），移动端单列堆叠。

### 4.4 降级规则

- `analysis_mode=single`（无基准）：隐藏基准系列列、超额 KPI、③超额线、⑥超额直方图，曲线区只画策略净值；
  明细区隐藏"指数"列，提示"当前数据无基准序列"。
- `series` 缺失（未传 `include_series` 或 single 模式）：③ 区显示说明占位，不显示空图。
- `sheet_result` 不存在：⑧ 区对应 tab 隐藏（§7）。

## 5. 图表规划（三梯队）

### 第一梯队（核心，依赖后端 series）

| 图 | 类型 | 数据 |
|---|---|---|
| 净值曲线 | 折线 ×3（基准/策略/超额），hover 联动 tooltip，可切对数轴 | `data.series` |
| 水下回撤曲线 | 0 以下填充面积图（策略，可叠加基准） | `series.start_nav` 逐点算 `nav/cummax-1`（纯展示变换，前端做） |

### 第二梯队（现有 metrics 即可）

| 图 | 类型 | 数据键 |
|---|---|---|
| 年度收益对比 | 分组柱（升级：柱顶数值标注） | `index/start_returns_rate.annual_return` |
| 年超额收益 | 柱（正红负绿） | `excess_returns.annualized_return_diff` |
| 年度最大回撤 | 分组柱 + 回撤日期 tooltip | `index/start_maximum_drawdown.year_maximum_drawdown` |
| 风险调整雷达 | 雷达图：夏普/索提诺/卡玛/月超额胜率/月波动率（归一化） | `*_sharpe_ratios.all`、`*_sortino_ratio`、`*_kama_ratio`、`monthly_excess_win_rate`、`*_monthly_return_volatility` |
| 月度收益热力图 | 年×月自绘 CSS 色块表（红涨绿跌，色阶按幅度），可切 指数/策略/超额 | `monthly_excess_returns`（含每月指数/策略/超额三列） |
| 月超额收益 | 柱（正红负绿）+ 12 月均线 | `monthly_excess_returns` |
| 滚动收益 | 组合图：均值（柱）+ 胜率（线，右轴），3/6/12 | `rolling_return_{n}_avg_return`、`rolling_return_{n}_win_rate` |
| 收益分布直方图 ×3 | 分组柱（基准 vs 策略），超额一张单系列 | `*_monthly_distribution_pct`、`*_days_distribution_pct`、`excess_distribution_pct` |
| 月度散点 | 散点 x=指数月收益 y=策略月收益 + 45° 参考线（右上半区=跑赢） | `monthly_excess_returns` |

### 第三梯队（专题区）

| 图 | 类型 | 数据键 |
|---|---|---|
| 极端行情对比 | 下跌/上涨阶段：均值收益分组柱 + 胜率/跑赢次数标注 | `*_downfall_*`、`*_upward_*` |
| 极端单日 | 涨跌天数对比柱 + 涨跌比 | `*_daily_gain_days/loss_days`、`*_daily_gain_loss_ratio` |
| 修复天数 | 条形图（指数/策略/超额 + 年度最大值） | `*_maximum_number_of_backtest_repair_days`、`year_*_yearly_max_repair_days` |
| 资金曲线特征 | 指标卡组：期初/期末净值、最大连涨/连跌月、创新高次数/频率/平均间隔 | `*_net_value_left/right`、`*_consecutive`、`*_new_high_*` |

图表库：继续 Chart.js（线/柱/混合/雷达/散点全覆盖），**改为本地 vendor**（`/static/js/` 固定版本），
内网/nginx 部署不依赖 CDN；热力图**自绘 HTML 色块表**（不引 matrix 插件，打印友好）。

| 全量 JSON | **保留（兜底）** | 明细 tab 11，默认折叠 |

新增 tab（V2 没有）：极端行情（七）、资金曲线特征（八）、月度/日度分布细表（4.2/5.3）、滚动收益。

## 7. Sheet 结果与任务跳转入口（新增问题 3）

### 7.1 sheet_result 是什么、怎么展示

- 仅 **Google Sheet 来源**返回（`sheet_reader.analyze_v1` 把模板 Sheet 的结果区读成键值对挂到 `results.sheet_result`）；
  结果 ID / 粘贴 / Excel 来源没有该键。
- 结论：**有则展示**——明细区 tab 9 条件渲染，键值两列原样展示（键名来自 C 模板 Sheet 本身，
  中英文混杂且随模板变化，**不做映射、不改名**；这是"Sheet 里写了什么就展示什么"的原始凭证）。

### 7.2 C 系列 / 回测跳转场景

- 跳转入口：`/performance-analysis/v3?task_id=<任务ID>` 或 `?result_id=<结果ID>`。
  页面加载读取参数：`task_id` → 自动调 results 投影接口填充结果下拉（V2 结果分析 Tab 的交互平移）；
  `result_id` → 直接分析。
- 该路径的响应**没有 `sheet_result`**（收益序列来自 return_series，不读 Sheet），Sheet 结果 tab 不出现。
  若未来要把"任务对应 Sheet 的结果区"带给结果分析，需要任务链路把结果区快照落库（如写入 TaskResult），
  属于后端增强，本期不做，tab 位已预留。
- 来源信息卡（顶部）展示任务/结果的 富信息：股票代码·名称·年份·参数 a/b·K线范围（fields 投影已有）。
- C 系列 4 个详情页与回测列表加跳转按钮：**后续项**（改对应详情页 JS 回填链接即可，V3 本身参数驱动，任何页面可链入）。

## 8. 统一指标中英文映射（新增问题 4）

### 8.1 结论

需要。现状：Word 报告的中文行名硬编码在 `strategy_backtest_report_service.py`（事实上的词表，但不对外）；
前端 V2 只有 14 条 `scalarNameMap`；其余全英文裸键。V3 建立**前端唯一词表**：

- 新建 `static/js/common/metric-names.js`（普通 script 原位置加载，与 `common/{api,utils,business}.js` 同层）：

```js
// 统一指标词表：key -> { zh: 中文名, group: 分组(对齐RPT-S八章), fmt: 'pct'|'ratio'|'nav'|'int', unit }
// 分组常量：RETURN / RISK / RISK_ADJUSTED / MONTHLY / DAILY / EXCESS / EXTREME / CAPITAL / SHEET
const METRIC_NAMES = {
    index_cumulative_return: { zh: '基准累计回报率', group: 'RETURN', fmt: 'pct' },
    start_cumulative_return: { zh: '策略累计回报率', group: 'RETURN', fmt: 'pct' },
    excess_cumulative_return: { zh: '累计超额收益', group: 'EXCESS', fmt: 'pct' },
    // ... 全量键
};
window.MetricNames = { get(key), zh(key), fmt(key, value), group(key) };
```

- V3 的 KPI、图表系列名、表头、全量指标总表**一律经词表取名**，页面不再出现英文裸键。
- 词表初稿以 Word 报告行名为准（累计回报率/年化收益率/年化波动率/最大回撤(MDD)/最大回撤修复天数(年度最大)/
  盈亏比(平均盈利/平均亏损)/月超额胜率(>0)/最大连涨月份/创新高平均间隔月…），吸收 V2 `scalarNameMap` 14 条。
- **"策略 vs 模型"叫法需定一个**：Word 报告用"策略"，V2 页面用"模型"。词表默认跟报告用**策略**，
  实施前与需求方确认一次即可（词表单点改）。

### 8.2 为什么放前端而不是 `app/constants/`

- 词表当前唯一消费方是前端页面；`app/constants/` 的定位是"被多个后端模块依赖的静态表"（AGENTS.md），
  Word 报告后端已有自己的行名，后端本期不消费词表，进去会造成单侧依赖。
- 若后续后端也要消费（如报告行名重构为引用词表），再按仓库规范落 `app/constants/metric_names.py`
  并评估同步机制——登记为后续项。
- Vue 侧（frontend/）未来做该页迁移时按"翻译不是重设计"原则搬这份词表。

### 8.3 sheet_result 键名不做映射

见 §7.1——键来自模板 Sheet，内容不可控，映射表维护成本高于收益；原样展示即"所见即所得"。

## 9. 多数据对比接入口（Dataset Registry）

### 9.1 三层结构

```
① 来源适配层 DataSourceAdapter（每来源一个，统一出口）
   sheet | paste | excel | result_id | url_param | （未来：组合方案G1/G2、多结果勾选）
   职责：把来源解析成标准三列收益行 [{date, index_return, start_return}] + meta（股票/年份/范围）

② 数据集层 DatasetStore（state.datasets[]）
   AnalysisDataset = { id, label, source, rows, metrics, series, meta, color }
   - label 如 "159682.SZ·2024·方案a2"；color 从固定色板自动分配
   - 每个 dataset 一次 analyze 调用（include_series: true），结果缓存于 dataset
   - 提供"当前参与对比"勾选集合；阈值重算只更新受影响 dataset 的 metrics

③ 渲染层（所有图表/KPI/表格函数签名统一 renderXxx(datasets[])）
   - 曲线类：每 dataset 一条策略线；基准线默认取第一个 dataset 的指数（可配置"各画各的"）
   - 柱状/表格/KPI：x=指标或年份，系列=dataset；KPI 总表每 dataset 一列
   - datasets.length > 1 时自动切对比模式（图例、色板、表格多列表头）
```

### 9.2 约定

- **时间轴对齐**：日期并集做 x 轴、缺失置 null（断线）；不强制对齐重采样。
- **超额口径**：超额 = 各 dataset 自己的基准；多 dataset 对比时图例标注"各自基准"，不合并口径。
- **后端接口**：本期不加批量分析端点——前端每 dataset 循环调用现有 `analyze`，注意
  `rate_limit_analyze` 限流（参考 Word 导出 2 秒间隔做法）；未来若需一次对比几十个，
  批量载荷加在 analyze 入口（`data: [...]`），接入口位置已在 Store 层预留，图表层不动。
- V2 单数据集行为不变：datasets.length === 1 时即"指数 vs 模型"现状语义。
