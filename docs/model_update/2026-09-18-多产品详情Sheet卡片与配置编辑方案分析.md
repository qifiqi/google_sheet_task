# 多产品详情 Sheet 卡片与配置编辑方案分析

日期：2026-09-18　分支：dev_vue　范围：多产品回测（backtest_multi_product）详情页

## 一、本次修改：任务运行配置内新增产品 Sheet 卡片

### 需求

多产品任务详情页"任务运行配置"内，以卡片形式展示每个产品的 Google Sheet；卡片拼接标准谷歌 Sheet 地址，点击跳转。

### 修改点（Vue 与静态版同步）

| 文件 | 修改 |
| --- | --- |
| `frontend/src/views/backtest-multi/Detail.vue` | "任务运行配置" tab 下方新增"产品 Google Sheet"卡片区；`sheetCards` computed + `buildGoogleSheetUrl()`；卡片样式 |
| `templates/backtest_multi_product/detail.html` | `#taskConfigGrid` 下方新增 `#taskSheetSection`/`#taskSheetGrid` 容器（无产品时 `d-none`） |
| `static/js/pages/backtest_multi_product_detail.js` | 新增 `renderSheetCards()`，在 `loadTaskDetail()` 内 `renderTaskConfig()` 之后调用 |
| `static/css/pages/backtest_multi_product_detail.css` | 新增 `.task-sheet-*` 样式（网格/卡片/悬停） |

### 行为说明

- 地址拼接：`https://docs.google.com/spreadsheets/d/<spreadsheet_id>/edit`，与既有 `backtest/Create.vue`、`admin/GoogleSheets.vue`、静态版 `backtest_training_create.js` 的 `buildGoogleSheetUrl` 格式一致。
- 数据来源：`task.config.products[].sheet.{spreadsheet_id, sheet_name, title}`；`spreadsheet_id` 由后端 `normalize_multi_product_config` 强校验必填（`app/services/backtest_multi_product_service.py`）。
- 整卡可点：有 `spreadsheet_id` 时整卡为 `<a target="_blank" rel="noopener noreferrer">`；缺失时降级为不可点卡片，CTA 提示"缺少 spreadsheet_id，无法跳转"。
- 卡片内容：产品名 + 模型标签（C3/C5/C7，复用 `inferProductModelVersion`）、股票/市场 · 比例、Sheet 标题、工作表名。

## 二、分析：多产品任务 config 的编辑怎么做

### 现状与问题

1. **管理端裸 JSON**：`admin/Tasks.vue` 编辑弹窗是 JSON textarea，提交 `PUT /api/tasks/{id}/config`；后端 `TaskConfigUpdateSchema` 只约束 `config: dict`，无任何字段级校验——手写 JSON 易错且错了也不报（用户痛点）。
2. **C3 专用弹窗有丢字段隐患**：`task/Detail.vue` 的"编辑配置"弹窗保存时**重建** config 只保留 9 个字段，`token_type/token_id/kline_data_source` 等未建模字段会被丢弃。此模式不可直接照抄到多产品。
3. **multi_product config 结构深**：由 `backtest-multi/Create.vue` 表单生成——`start_date/end_date/token_id/fixed_product_batch_id/weighting_mode/products[]`，每个产品含 `sheet{spreadsheet_id,sheet_name,title}` 与 `parameters` 二维数组（C3/C5/C7 三套参数列）。手写 JSON 极易出错。
4. **服务层现状**：`update_task_config`（`app/services/task/creation.py`）仅拒绝 running 任务；`_normalize_task_config_for_type` 只归一化不校验；仅 `backtest_training` 有 sheet 校验。
5. **创建页可复用性**：`backtest-multi/Create.vue` 无 restart/模板回填分支、无 localStorage 草稿（与 C 系列不同），接入"编辑模式"不需要处理草稿互斥；`extractSpreadsheetId` 已存在可复用。

### 方案对比

**方案 A（推荐）：创建页复用 + 编辑模式**

- `Create.vue` 支持 `?edit_task_id=<id>`：进入时拉取任务 → config 回填表单（参照 `CreateC7.vue` 的 `normalizeC7Config + applyConfig` 范式做归一回填）→ 编辑态下标题/按钮文案切换，提交改调 `updateTaskConfig`（PUT），成功后跳回详情页。
- 提交 payload 组装完全复用 `collectProducts()/buildTaskProductGroups()`，表单是字段唯一来源，天然避免手写 JSON 错误；保存前以原 config 为底做 merge，防止漏掉表单未覆盖的字段（如 `token_name/token_file` 等后端注入字段）。
- `Detail.vue` 增加"编辑配置"按钮（running/pending 执行中禁用），跳转创建页编辑模式；保存成功后提示"配置已保存，可通过断点重启/重头开始生效"。
- 注意点：`fixed_product_batch_id`、`token_id` 等在编辑态应保留原值（token 可允许换选）；多产品任务是成批创建（每组一个任务、共用批次号），编辑入口在单任务详情页，语义是**只改该任务**，不做跨任务批量编辑。

**方案 B：详情页内嵌结构化弹窗（照抄 C3 弹窗模式）——不推荐**

products 编辑器（每产品的参数表 + sheet + 比例）远比 C3 的 9 字段复杂，在弹窗里重建一份必然与创建页漂移；C3 弹窗丢字段就是这种"重建式保存"的前车之鉴。

**方案 C：管理端 JSON 编辑器增强（monaco + JSON Schema 校验）——治标不治本**

能挡住语法错误和明显类型错误，但用户仍要理解 config 结构；可作为管理端兜底保留，不解决根本问题。

### 后端配套（任一方案都需要）

- `TaskConfigUpdateSchema` 目前仅 dict 级校验。为 `backtest_multi_product` 增加类型化校验：`update_task_config` 按 `task_type` 分发，复用 `normalize_multi_product_config` 的必填校验（`start_date/end_date/products[].sheet.spreadsheet_id`），非法字段显式报错而非静默存库。
- 保持 running 拒改语义；编辑对 pending 任务立即生效（启动即用新 config），对已完成/失败任务通过重启生效（restart 读 config）。

### 方案 A 落地清单

1. `Create.vue`：`edit_task_id` 路由参数、`loadEditTask()` 回填、`isEditMode` 状态切换文案与提交目标（`createTask` → `updateTaskConfig`）、成功后回详情。
2. `Detail.vue`：工具栏加"编辑配置"按钮。
3. 后端：multi_product config 类型化校验（schema 或服务层复用 normalize）。
4. 同步检查（AGENTS.md 清单）：表单初始化、restart 回填、提交 payload 的 POST/PUT 切换（本页无 localStorage 草稿，无需处理草稿互斥）。
