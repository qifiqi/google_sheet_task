# 修改文档：权重组合分析新增「产品选择 + 单股范围」

- 日期：2026-09-18
- 分支：dev_vue
- 范围：绩效分析权重组合页（`/performance_analysis/weight_combination`）及其接口
- 性质：功能扩展（新增可选入参，旧请求逐位兼容），**不修改数据库 schema/迁移/数据**

## 背景与目标

原权重组合分析只能对任务下**全部**成功结果做组合，且单只股票的权重上限是**全局统一**的一个值
（`single_cap`，如 30%），枚举区间固定为「每只 0 ~ single_cap」。这带来两个痛点：

1. 任务下产品多于所需时无法只挑其中几只参与组合（且产品数 > 5 直接拒绝）。
2. 无法表达"某只股票最多/最少配多少"——例如按任务配置比例，A 股只应配 10%、B 股可配 50%。

本次改造把枚举区间从"全局单值"升级为"逐产品区间"，并在页面参数区下方新增
**产品选择 + 单股范围**面板：填好任务 ID 后自动拉取任务下的产品列表，
默认勾选全部可用产品（配置比例为 0 的产品除外——它在组合里本就不参与），
单股范围默认 `0 ~ 任务配置比例`（按步长向下取整），可自由修改。

## 交互口径（前端）

- **加载时机**：任务 ID 输入框失焦/回车（`change`）或 URL 带 `?task_id=` 时自动加载；
  「重新加载」按钮可手动刷新。切换任务时旧请求被 abort，过期响应按请求序号丢弃。
- **产品行**：勾选框 + 股票名/代码 + 配置比例 + 单股下限 + 单股上限。
  - 配置比例取自任务配置 `config.products[i].ratio`（按结果参数中的 `product_index` 定位），
    任务配置缺失时回退到执行结果 `parameters.ratio` 快照；都没有则显示 `-`，
    默认上限回退到「单股上限」输入框的值（单产品/训练任务的场景）。
  - 成功但**没有收益序列**的结果仍列出（勾选框禁用 + 提示），让"某产品为什么没进组合"可见。
  - 未勾选/不可用的行淡出且输入框禁用；「全选」「重置范围」作用于可用产品。
- **默认范围取整**：`max = floor(min(配置比例, 100) / step) * step`。
  向下取整保证"0 ~ 配置比例"语义不被突破（如比例 33.3333%、步长 5% ⇒ 上限 30%）。
- **提交校验**（与服务端同规则，先失败先提示）：至少选 1 只；`0 ≤ 下限 ≤ 上限 ≤ 100`；
  上下限必须为步长整数倍；面板启用后 `single_cap` 不再参与校验与枚举，
  且**该字段不再随请求发送**（服务端此时不读它，但它的字段级范围约束 `>0 / ≤100`
  仍会生效，发送一个"不生效的值"反而会卡住请求）。
- **加载中不提交**：任务 ID 变更由输入框失焦触发加载，紧接着的提交会读到上一个
  任务的产品与范围；`productsLoading` 期间提交直接提示「产品列表加载中」并中止，
  避免把旧范围发给新任务（服务端会以"单股范围包含未参与组合的产品"拒绝）。
- **执行中**：面板整体禁用，避免结果与参数不一致；取消/结束后恢复。

## 接口契约

### 新增：`GET /performance_analysis/v1/weight_combination/products?task_id=...`

- 鉴权：`login_required`；请求校验：`WeightCombinationProductsQuerySchema`（`task_id` 必填）。
- 返回 `{"task_id","task_type","products":[{"result_id","product_index","stock_code","stock_name","has_returns","ratio"}]}`，
  列表顺序与枚举装载顺序一致（`step_index` 升序，见 `list_preview_entities`），
  前端按 `result_id` 回传，二者不会错位。

### 扩展：`POST /performance_analysis/v1/weight_combination`

新增两个可选入参（缺省时行为与改造前完全一致）：

| 字段 | 语义 |
|---|---|
| `result_ids: [int/str]` | 参与组合的产品白名单（TaskResult 主键）。缺省 = 全部可用产品；空数组 = 拒绝（见下方状态码说明）。 |
| `stock_ranges: [{result_id, min_weight, max_weight}]` | 逐产品权重范围（%）。必须**恰好覆盖**参与组合的产品：缺项、含未选中产品、重复 ID 均拒绝。 |

约束（schema 层，`app/schemas/performance_analysis.py`）：

- 范围上下限必须是 `step` 的整数倍、`min ≤ max`、`0 ~ 100`，同产品不得重复。
- **提供 `stock_ranges` 时 `single_cap` 的网格/下限校验被跳过**（该字段此时不参与枚举，
  避免用一个不生效的字段卡住请求）；未提供时校验保持原样。
  注意 `single_cap` 的字段级范围约束（`gt=0`、`le=100`）与是否提供范围无关，
  因此前端在启用范围后直接不发送该字段。

约束（service 层，`app/services/performance_analysis/service.py`，错误信息列出具体 ID）：

- 选中的 `result_id` 不存在或没有可用收益序列。
- 无解剪枝：`Σ单股上限 < 组合总权重下限`、`Σ单股下限 > 组合总权重上限`、`Σ单股上限 = 0`。
- 规模保护改为 `∏(max_units_i − min_units_i + 1) > MAX_CARTESIAN_SIZE(10万)` 拒绝；
  **未提供 `stock_ranges` 的兼容链路仍保留 `n ≤ 5` 硬限制**，提供范围后不再受该限制。

**状态码口径（实测，2026-09-18）**：本接口是 NDJSON 流式响应，service 层抛出的
`ValidationError`（未知/未选中的产品、范围缺项或越界、空选、甚至任务不存在）都在
生成器内被 `app/routes/performance_analysis_api.py` 捕获，**返回 HTTP 200 +
一行 `{"error": true, "message": "..."}`**，由页面按 error 行弹提示（
`weight_combination_tabulator.js` 读到 error 行即 `throw`）。只有 `parse_body`
阶段（Pydantic 校验，如步长网格、`task_id` 缺失）才返回 400 信封。
该形态是改造前既有行为（缺失任务同样如此），本次未改动；只有新增的
`GET .../products` 是普通 JSON 接口，任务不存在按全局异常体系返回 404。

枚举实现要点：把原来的"统一 `cap_units`"改为逐产品 `(min_units, max_units)`，
回溯时用后缀和约束 `lo = max(min_i, remaining − Σmax_{>i})`、`hi = min(max_i, remaining − Σmin_{>i})`，
保证每个中间态都能被后续产品填满；下限向上取整、上限向下取整，均不越过用户填写的意图。

## 兼容性

- `result_ids`/`stock_ranges` 缺省 ⇒ 产品集、`cap_units`、`n ≤ 5`、规模上界与旧实现逐值等价（组合顺序不变）。
- 接口返回结构（`stocks`/`annualized_rates`/`year_max_drawdown`）零变化，页面表格、CSV 导出、全局预览跳转不受影响。
- 产品列表接口只读任务与结果表，不写任何状态；配置比例解析失败（非多品任务/历史脏配置）静默降级为无比例。
