# 接口规范审计与修复（2026-09-28）

## 背景

对 `app/routes/` 全部 18 个 API 路由文件（约 90+ 端点）按 2026-09 数据层重构规范
（`docs/design/data-layer-refactor/04`）做一致性审计，并修复其中两处偏差。

## 审计结论

核心红线规范全库强一致：

| 维度 | 结果 |
|---|---|
| 响应信封唯一出口（`api_response.success/error/paginated`） | 100% 统一，零直接 jsonify、零手写信封字典 |
| 分层（routes 不碰 repository/ORM） | 100% 统一 |
| 异常体系（routes 不 catch，交 `errors.py`） | 基本统一，1 处红线违规（本次已修） |
| 鉴权（`login_required`/`admin_required` 单一接缝） | 统一 |

已知债务（登记不处理）：

- URL 前缀存在多套约定（`/api/*`、`/api/exports/*`、`/admin/api/*`、
  `/backtest-training/api/*`、`/performance_analysis/*`、`/meta/*` 等），
  `errors.py` 靠 Accept 启发式兜底，前端 `api.js` 隔离，收敛成本高收益低；
- 分页助手 `paginated()` 仅 3 个文件采用，其余按形状约定手写（契约未破）。

## 本次修复

### 1. 流式接口 `str(e)` 泄漏（红线）

`app/routes/performance_analysis_api.py` 权重组合 NDJSON 流式端点原样下发
`str(e)`，违反 `errors.py` "错误响应绝不携带内部信息"红线。改为按异常类型分流：

- `AppException`：文案本身面向用户（与信封同源），随流末行下发 `exc.message`；
- 其它异常：`logger.exception` 记详情，只下发通用文案。

### 2. 分页参数解析统一（`parse_pagination`）

`app/utils/request_parsing.py` 新增 `parse_pagination(default_page, default_per_page,
max_per_page)`，统一"缺失/非法回落默认值、下限 1、可选上限"的边界规则，收编：

- `app/routes/backtest_api.py`（`_make_task_results_by_task_id_view`，默认 1/10、上限 100）；
- `app/routes/scheduler_api.py`（定时任务列表，默认 1/50）。

**豁免**：`app/routes/result_api.py` 的任务结果列表保持可空分页参数——
"不带 page/per_page 返回全量"是 CSV 全量导出依赖的既有语义，不适用本助手。

### 查询参数解析约定（明文化现状）

- body 一律走 `parse_body`（Pydantic v2）；
- 复杂/需校验的 query 走 `parse_query`；
- 简单标量 query（筛选项）允许 `request.args` 直读；
- 分页参数一律 `parse_pagination`，不再手写 `max(min(...))` 钳制。
