审查范围：`dev_db_to_http` 分支（HEAD dc20392f），静态审查 + 远端真实 HTTP 实测（测试账号，只读操作）。

## 实测通过项（契约面健康）

- 统一信封 `ret_code/ret_msg/ret_count/ret_obj` 与 `client.py` 解包逻辑一致；`ret_obj` 字段为 snake_case。

- `ParamTasks/ParamTaskResults/ParamSystemConfigs` 分页 + `ret_count` 正常；`StockData/GetDataAllList` K线返回完整 wire 字段（stock_open/stock_max/stock_min/stock_close/stock_volume/stock_volume_price），单月区间 ~190ms。
- 代理获取已收口统一出口（`proxy_manager` → `stock_api.stock_dic.get_proxy_list_by_one()`）。
- 方案B启动对账顺序正确：`reconcile_all_runtime_states` → `namespace_reset` → `check_and_cleanup_dead_tasks`（startup.py:772-791）。
- 调用器出站布尔 0/1 编码、失败日志脱敏（token/password 类键名打码）落实。

## P0-1 崩溃恢复断链：启动期占用清理清的是本地库，真实占用态在远端

`app/startup.py:363-385` 三个启动函数在 http 模式下全部操作**本地 ORM 表**：

- `reset_google_sheet_token_occupancy()` 清本地 `GoogleSheetToken.current_in_use_count`，真实计数在远端 `param_google_sheet_tokens`；
- `reset_google_sheet_occupancy()` 清本地 `GoogleSheet.is_in_use`，真实占用在远端 `param_google_sheet`；
- `cleanup_stale_backtest_sheet_run_locks()` 删本地 `BacktestSheetRunLock`，真实锁行在远端 `param_backtest_sheet_run_locks`。

且获取端**无惰性自愈**：`occupancy.py:96-107` 校验只看 `is_in_use`/`current_task_id`，不校验持有任务是否还存活；`backtest_repository.acquire_lock`（http_backend:432）见他任务持锁即失败。

**后果**：进程崩溃/强杀后，远端 Sheet 占用、Token 使用计数、运行锁全部残留且永不释放——相关 Sheet/Token 对后续任务永久不可用，需人工清远端表。同理 `check_and_cleanup_dead_tasks`（startup.py:684+）读本地 `Task.query`，http 模式下读的是陈旧本地库，远端 running 里程碑行无人复位。

**修复方向**：三个 reset 与死任务清理改为走 http 仓储（远端按 task_id/状态过滤清理），或为占用行引入持有任务存活校验的自愈语义。

## P0-2 服务级凭据 STOCK_API_TOKEN 无生命周期管理，当前配置缺失

- 仓储层所有调用不带用户 token：任务线程、调度器、启动钩子无请求上下文；业务 API 路由的仓储调用同样不传 token。**全部数据访问回退 `STOCK_API_TOKEN`**；用户 token 只用于 `GetUserInfo`/`GetUserRoleList` 身份与菜单。
- `.env` 与 `.env.example` **均无 `STOCK_API_TOKEN` 条目**——当前工作区 http 模式下任务执行、启动钩子、业务 API 全部 401（实测无 token 请求 → ret_code=401）。
- 远端 token 为会话票据（实测可被服务端判失效），TTL 未知；本服务无自动重登/刷新（refresh 端点已注释，前端 401 靠人工重登）。**后台任务线程无人可重登：token 一过期，长驻部署的所有数据访问开始失败**。

**修复方向**：与远端确认长效服务凭据（API key）或由本服务保管账密 + 401 时自动重登换 token；`.env.example` 补条目与获取方式；启动期对服务 token 做一次探活。

## P1-2 网关每请求同步 GetUserInfo：无缓存、无熔断

`app/__init__.py:93` 全局 `before_request` → `authenticate_current_request`（app/utils/auth.py:205）每请求一次远程 `GetUserInfo`（实测 ~45ms）。路由表有 60s TTL 缓存（sys_user_repository.py:12），**身份校验没有任何缓存**，也无负缓存/熔断：

- 远端抖动时每个请求都阻塞至 `STOCK_API_TIMEOUT`（默认 10s）→ worker 池被占满 → 全站雪崩；
- 远端身份服务宕机 = 本服务全站 503（单 Token 架构固有，无缓存放大之）。

**修复方向**：身份校验结果按 token 加短 TTL 缓存（如 30-60s）+ 失败负缓存（如 5s 内不再回源，直接 503）。

## P2-3 安全与隔离（2026-10-17 复核修正）

**远端确有按端点权限体系**（实测修正此前"无权限"的误判）：fuqing_test 访问
`SysUser/GetDataByPageList`、`SysRole/GetDataByPageList`、`SysModel/GetDataByPageList`、
`PwdReset`、`UpdateUserRole`、`UserEnableOrUnEnable` 一律 `ret_code=403 您无权进行此操作`；
`param_*` 业务端点与 `SysUser/GetListForSelect` 放行。权限粒度按账号角色 × 模型
（GetUserRoleList 返回该角色可访问的 33 个模型）。

仍然成立的事实与风险：

- **本服务的数据访问不带用户 token**：仓储层所有 param_* 调用（含业务 API 路由、
  后台任务线程、启动钩子）都走服务级 `STOCK_API_TOKEN`；用户 token 只用于
  `GetUserInfo` 身份校验、`GetUserRoleList` 菜单与登录代理（代码证据：仅
  `sys_user.py` 控制器三个方法带 `token=`，`g.current_token` 全库无业务消费点）。
  因此远端按角色模型的数据权限对本服务全部用户都以**服务账号的角色**评估，
  不区分实际操作者；子服务用户能看什么取决于服务账号的角色配置。
- `ParamSystemConfigs/GetDataByPageList` 对 fuqing_test 明文回传
  `api_secret_key` 等 value（该账号角色含此模型即放行）——服务账号的角色若
  含系统配置模型，任何子服务用户都可通过本服务读到，角色收敛需在主站侧做。
- `StockDic/GetProxyListByOne` 明文代理账密（同上，按角色放行）。
- `client.py:_build_transport` 只校验 scheme 不校验 host（localhost/私网可配）；
  requests 默认跟随重定向且带 Token 头——建议 host 校验 + 禁跨 host 重定向。

## P3 性能退化与死接口

- E1~E8 远端增量端点 **0/8 落地**，对应 27 处 `TODO(db-to-http)` 退化策略（全量拉取内存过滤、逐 id 删除、逐状态逐日聚合、双键排序等）均在 README §6.2 登记，量小可撑，量大前需排期。
- 控制器 `stock_data.get_stock_list_by_code` 本仓无调用方（死接口），且实测远端对应端点对大区间请求挂起 >2 分钟——建议删除控制器方法或在 docstring 标注远端缺陷，避免误用。
- 按用户 token 的 transport 缓存满 64 个时整体 `clear()`（client.py:204），全量重建连接池；现网用户量小无感。
- 远端测试库存在脏数据（`unsupported_task` 类型任务、多条 owner=None），不影响本仓但会干扰联调判断。

## 修复优先级建议

1. P0-2（服务凭据）：阻塞一切部署，先与远端确认长效凭据方案。
2. P0-1（占用恢复）：补远端清理路径，否则一次崩溃即需人工进库。
3. P1-1 两条 AttributeError：`list_by_task_fields` http 孪生可先用全量拉取+投影兜底实现，一天内可消掉。
4. P1-2 GetUserInfo 缓存：改动小收益大。
5. 其余按 README §8 路线随 E1~E8 推进。
