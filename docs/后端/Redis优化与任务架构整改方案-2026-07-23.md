# Redis 优化与任务架构整改方案

更新时间：2026-07-23

当前执行进度：

- `P0` 未开始
- `P1` 未开始
- `P2` 未开始
- `P3` 未开始

## 1. 结论

项目适合引入 Redis，但不能把 Redis 当作 PostgreSQL 的替代品。

Redis 应承担三类可丢失或可重建的能力：

- 任务投递与 worker 间协调
- 外部 API 的分布式限流
- 跨 Gunicorn worker 的共享缓存

`Task`、`TaskLog`、`TaskResult`、任务断点、Google Sheet 占用、Token 占用和回测 Sheet 锁必须继续以 PostgreSQL 为唯一事实来源。

## 2. 当前问题

生产 Docker 使用 Gunicorn 启动，worker 数为 `CPU * 2 + 1`。但任务系统的 `running_tasks`、`task_stop_events`、`start_errors` 与部分 Token 运行态保存在进程内存。

因此多个 Web worker 同时运行时存在以下风险：

- 全局并发上限被按 worker 重复计算
- 取消、重启和本地线程状态检查只能命中创建任务的 worker
- 看门狗重启计数不在 worker 间共享
- Web worker 重启会丢失本地运行态

相关实现：

- `config/gunicorn.conf.py`
- `app/services/task/facade.py`
- `app/services/task/runtime.py`
- `app/services/task_watchdog.py`

此外，Docker 以 `gunicorn ... run:app` 启动，但 `bootstrap_app(app)` 仅在 `run.py` 的 `__main__` 分支调用。后续整改时必须先确认生产启动路径是否实际执行了启动期 schema 修补、资源占用清理、调度器和看门狗初始化。

## 3. P0：任务执行与外部限流

### 3.1 用 Redis 作为任务 Broker，拆分 Web 与任务 worker

#### 目标

Web 进程只负责鉴权、创建任务记录和投递任务；独立 worker 负责执行 Google Sheet 与回测任务。

#### 方案

1. 使用成熟任务框架的 Redis broker，例如 Celery + Redis。
2. 队列消息只传递 `task_id`，worker 再从 PostgreSQL 读取最新任务配置。
3. 状态流转仍写入 PostgreSQL：`pending -> running -> completed/error/cancelled`。
4. 取消操作更新数据库状态；worker 在既有步骤边界检查取消状态，不依赖强制终止进程。
5. 重试、断点恢复、Token/Sheet 释放继续沿用现有任务层逻辑，不在 Redis 存放唯一副本。
6. 先保留 APScheduler 的数据库抢锁与现有子进程清理任务，不在本阶段迁移定时任务。

#### 验收标准

- 任意 Web worker 创建的任务均可被任意任务 worker 消费。
- Web worker 重启不会丢失待执行任务。
- 多个 Web worker 下，全局并发数不会超过配置值。
- 取消、重启、网络重试和资源释放的回归测试全部通过。
- PostgreSQL 中的任务状态始终可独立解释任务最终状态。

### 3.2 外部 API 分布式限流

#### 场景

东方财富 K 线、股票搜索、Yahoo K 线和 Google Sheet API 都会被多个任务 worker 并发调用。当前有网络重试与 Token 并发占用，但没有跨 worker 的请求频率限制。

#### 方案

使用 Redis Lua 脚本实现原子令牌桶，按以下维度分别限流：

- `provider + api_kind`：东方财富搜索、东方财富 K 线、Yahoo K 线、Google Sheet
- Google Sheet API 额外包含 `token_id`
- 代理请求额外包含脱敏后的 `proxy_profile_id`

Redis key 示例：

```text
ratelimit:v1:dfcf:kline
ratelimit:v1:google-sheet:{token_id}
ratelimit:v1:dfcf:kline:{proxy_profile_id}
```

无法获得令牌时应按任务级可取消等待或延后重试，不能忙等，也不能把上游 `429` 当作普通业务失败。

#### 验收标准

- 多 worker 并发时，上游 QPS 不超过配置值。
- 限流等待可以响应任务取消。
- 限流统计可在日志或监控中查看。

## 4. P1：高价值共享缓存

### 4.1 K 线原始数据缓存

#### 场景

各任务服务会重新创建东方财富或 Yahoo 客户端并拉取 K 线。多品回测仅在单次任务内部维护 `kline_cache`，跨任务不能复用。

#### 方案

缓存原始 K 线，不缓存经过任务参数计算后的结果。

```text
cache:kline:v1:{source}:{market}:{stock_code}:{interval}:{adjustment}:{start}:{end}
```

- 历史截止日期早于当日：TTL 7-30 天。
- 包含当日行情：TTL 5-15 分钟。
- 缓存未命中采用短时互斥锁，避免同一标的被大量任务同时回源。
- key 必须包含数据源、市场、复权方式、周期和日期范围。

#### 验收标准

- 相同 K 线请求在 TTL 内不重复访问上游。
- 切换复权方式、数据源、日期范围或周期不会误命中。
- Redis 故障时自动回源，不阻塞任务执行。

### 4.2 股票搜索缓存

#### 场景

`/api/search-stocks` 每次调用东方财富搜索，并把结果写入 `stock_metadata`；当前未先使用已保存的元数据。

#### 方案

1. 先将 `stock_metadata` 改成 read-through 的持久化缓存。
2. 对高频搜索前缀再加 Redis 缓存。

```text
cache:stock-search:v1:{normalized_keyword}:{page_size}
```

- 正常结果 TTL 5-60 分钟。
- 空结果或上游无匹配结果 TTL 1-5 分钟。
- 上游异常不缓存为“无结果”。

### 4.3 Google Sheet 工作表列表缓存

#### 场景

当前已经使用 5 天 TTL 的进程内字典缓存；多 worker 和重启后无法共享。

#### 方案

```text
cache:worksheet-list:v1:{spreadsheet_id}:{token_id}:{proxy_profile_id}
```

- 不得把 token 内容、token 文件路径或代理密码放进 Redis key。
- 默认 TTL 可保留 5 天，但必须增加“强制刷新”与配置变更后的主动失效能力。

### 4.4 多品回测全局预览缓存

#### 场景

当前仅有 64 条进程内 LRU。预览会读取和解析大量 `TaskResult` JSON，无法跨 worker 复用。

#### 方案

```text
cache:multi-preview:v1:{task_id}:{ratio_signature}:{result_version_hash}
```

- 用 SHA-256 摘要作为 key 的可变部分，不把完整结果签名直接作为 key。
- TTL 5-15 分钟。
- 每次任务写入结果、删除结果或保存比例后删除该任务的预览缓存。

### 4.5 系统配置共享缓存

#### 场景

`ConfigManager._cache` 仅在当前进程有效，配置更新无法立即同步所有 Gunicorn worker。

#### 方案

```text
cache:system-config:v1:{key}
```

- TTL 60-300 秒。
- 配置写入、删除、批量更新时主动 `DEL` 对应 key。
- 通过 Redis Pub/Sub 通知各进程清理本地一级缓存。

## 5. P2：按监控决定是否实施

### 5.1 仪表盘与任务列表统计缓存

仪表盘会组合任务、结果、XPL 作业和资源健康等多组聚合查询；任务列表也包含分页、统计和平均时长查询。

- key 必须包含用户权限范围或允许的任务类型。
- TTL 5-15 秒。
- 创建、完成、取消、重启任务后主动失效。
- 先检查 PostgreSQL 索引和 SQL 执行计划，不能用缓存掩盖慢查询。

### 5.2 模型汇总与结果分析响应缓存

- 对模型汇总筛选、C3 汇总、单个结果分析使用 30-120 秒短缓存。
- key 必须包含筛选参数、任务结果版本和权限范围。
- 不缓存导出文件内容，也不缓存超大结果列表。

### 5.3 代理健康状态共享

`SmartProxyManager` 当前为进程内单例。Redis 可记录代理健康分、失败冷却窗口与当前候选，减少多个 worker 重复探测。

- 不把代理账号密码写入 key、日志或 Pub/Sub 消息。
- 代理状态只能作为调度提示，连接失败仍须在任务进程真实确认。

### 5.4 任务创建幂等键

为创建任务和 C31 批量创建接口支持 `Idempotency-Key`：

```text
idempotency:task-create:v1:{user_id}:{request_key}
```

- TTL 24 小时。
- 保存请求摘要与创建结果。
- 数据库唯一约束或业务校验仍是最终兜底。

## 6. P3：暂不优先

### 6.1 实时推送

Redis Pub/Sub 配合 SSE 或 WebSocket 可以替代日志页 15 秒轮询、模型汇总重建状态的 2 秒轮询。

当前前端轮询量有限，先完成 P0/P1 后再根据连接数和轮询压力决定。引入实时推送时必须补齐连接鉴权、断线重连和数据库回补查询。

### 6.2 低频目录数据缓存

导航、模板、枚举、角色权限等数据量小、更新少，可以缓存 5-30 分钟，但收益较低。权限缓存失效错误会产生越权窗口，默认不作为优先事项。

## 7. 明确不使用 Redis 的位置

以下数据不得只存 Redis，也不应在没有明确收益时改为 Redis：

- `Task`、`TaskLog`、`TaskResult`、`TaskResultReturn`
- 断点、自动重启次数的最终记录、任务错误摘要
- `BacktestProductResultCache` 固定产品结果缓存
- Google Sheet 占用、`BacktestSheetRunLock`、Google Sheet Token 占用
- XPL 分析作业领取、状态和重试记录
- JWT 黑名单、用户 Session 与权限快照
- 定时任务的数据库锁与执行记录

这些数据需要事务、查询、审计和重启恢复能力。若 Redis 同时保存副本，只能做加速层，不能形成第二个状态真相。

## 8. 部署与运维要求

Redis broker 与缓存不能使用同一套淘汰策略：

- 任务 broker：启用持久化，使用 `noeviction`，设置告警和容量冗余。
- 缓存：可单独实例或独立逻辑库，使用设置 TTL 的淘汰策略。
- Redis 连接失败时：缓存和限流按明确策略降级；任务 broker 不可静默降级为 Web 线程执行。
- 禁止在 Redis key、日志和监控标签中写入 token 原文、代理密码或完整 Google Sheet 凭据。

## 9. 推荐实施顺序

1. 核实并修复生产启动路径，确认 `bootstrap_app()` 在生产中仅执行一次且职责明确。
2. 建立 Redis 基础配置、健康检查、监控与故障演练。
3. 落地 P0：独立任务 worker、全局并发与上游限流。
4. 落地 P1：K 线、股票搜索、工作表列表、全局预览、系统配置缓存。
5. 用命中率、上游请求量、任务耗时、Redis 内存和错误率评估 P2/P3。

## 10. 回归测试清单

- 多 Web worker 创建任务时，不重复启动且全局并发受控。
- Web worker 重启后，已投递任务仍能执行或按数据库状态恢复。
- 取消任务后，worker 不会把任务回写为 `completed`。
- Redis 缓存命中、未命中、过期、主动失效和 Redis 不可用均有定向测试。
- 同标的不同复权方式、日期区间、周期和数据源的 K 线不会串缓存。
- 配置更新后所有 Web worker 都能读取新配置。
- 限流触发后不会产生忙等，任务取消能中断等待。
- Token、Sheet、回测锁和 XPL 作业在 Redis 故障时仍保持 PostgreSQL 一致性。
